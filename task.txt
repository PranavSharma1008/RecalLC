--------------------------------------------------------------------------------
1. PRODUCT VISION
--------------------------------------------------------------------------------

RecallLC solves a common DSA learning problem: students solve LeetCode
questions but forget their approaches after a few days.

The extension detects when the user opens a new LeetCode problem and shows a
small, non-intrusive reminder for an older problem that is due for revision.

Example flow:
  - User opens "Number of Islands".
  - RecallLC detects that "Climbing Stairs" was attempted three days ago and
    is due for revision.
  - A compact card appears in the bottom-right corner:

      +------------------------------------+
      | (symbol) TIME TO REVISE!  2 days late
      +------------------------------------+
      | Climbing Stairs                    |
      | [Medium] [Dynamic Programming]     |
      | Last attempted: 3 days ago         |
      | 2 attempts                         |
      | [ Revise Now ] [ Remind Tomorrow ] [ Dismiss ]
      +------------------------------------+

  - "Revise Now" opens the original LeetCode problem.
  - "Remind Tomorrow" snoozes it until the next local midnight.
  - "Dismiss" hides it for the rest of today WITHOUT rescheduling it.

3. LIVE RESEARCH FINDINGS — DO NOT RE-DO THESE
--------------------------------------------------------------------------------

These were established by probing the real LeetCode endpoints. They changed
several design decisions and are load-bearing.

  (a) POST https://leetcode.com/graphql  from curl  ->  403 Forbidden
      LeetCode's GraphQL is behind bot protection. It only answers requests
      that originate from a real browser session on leetcode.com.
      CONSEQUENCE: the content script (which runs on leetcode.com with the
      user's own session) must issue GraphQL requests — NOT the service
      worker, whose cross-origin fetch would not carry SameSite cookies.

  (b) GET https://leetcode.com/api/problems/all/  ->  200 OK (public, no auth)
      Returns 4087 problems with question__title, question__title_slug,
      difficulty.level, paid_only, total_acs / total_submitted.
      CONSEQUENCE: usable as a service-worker-side fallback for title and
      difficulty enrichment. It does NOT contain topic_tags.

  (c) GET https://leetcode.com/problems/two-sum/  from curl  ->  403
      The DOM can only be inspected in a live browser.
      CONSEQUENCE: the submission tracker must use resilient multi-selector
      fallbacks and fail silently rather than record wrong data.

  (d) Vite 8 uses Rolldown. `build.minify: 'esbuild'` fails with
      "transformWithEsbuild ... deprecated ... install esbuild separately".
      CONSEQUENCE: do not set `minify` in vite.config.ts at all (default 'oxc').

  (e) CRXJS 3.0.0 does NOT run a manifest-declared `content_scripts[].css`
      through Tailwind. It emits the raw source file, so the `@import
      "tailwindcss/utilities.css"` statements survive into dist and break.
      CONSEQUENCE (ALREADY APPLIED): remove `css:` from the manifest config and
      import the stylesheet from the content script instead —
        // src/content/content.tsx
        import '../styles/content.css';
      CRXJS then adds the built CSS to `content_scripts[].css` automatically.
      Verified: dist/assets/src-content-content-*.css is 25 KB with zero
      leftover @import statements.

  (f) Chrome >= 137 disables the `--load-extension` command-line switch by
      default. Use the DevTools `Extensions.loadUnpacked` command over
      `--remote-debugging-pipe` + `--enable-unsafe-extension-debugging`.

  (g) In a service-worker DevTools execution context, `chrome` is NOT defined.
      CONSEQUENCE: drive the extension's message API from an extension PAGE
      (popup/dashboard), not from the worker context.

  (h) `chrome.runtime.sendMessage` sent FROM the service worker does NOT reach
      the service worker's own `onMessage` listener.

  (i) Extension content-script assets appear in `web_accessible_resources`
      automatically (CRXJS default). Harmless but worth knowing.

4.2 REVISION ENGINE (src/services/revisionEngine.ts) — PURE FUNCTIONS
    Every function takes `now` as an argument; nothing calls Date.now() inside.
    That is what makes the whole scheduling model deterministic and testable.

    DEFAULT_INTERVALS = { forgot: 1, hard: 2, good: 5, easy: 14 }   (days)
    DEFAULT_INITIAL_INTERVAL_DAYS = 1

    nextDueDate(rating, reviewedAt, intervals) -> local midnight + days
    initialDueDate(lastAttemptAt, initialIntervalDays)
    isDue / isDueToday / isOverdue / overdueDays / daysUntilDue
    applyRating()  -> rating 'forgot' resets stage to 0; clears snooze/dismiss
    applySnooze()  -> sets snoozedUntil = next local midnight, NEVER touches dueAt
    applyDismiss() -> sets dismissedAt = now, NEVER touches dueAt
    isReminderEligible() -> excludes paused, snoozed, dismissed-today
    pickReminder() -> excludes the currently open slug
    sortByPriority() / priorityScore()
      overdue +1000 (+10 per overdue day, capped 500)
      due today +500
      struggleScore * 100
      attemptCount (capped 20)
      ties -> oldest dueAt -> slug (deterministic)
    computeStreak() -> consecutive days ending today or yesterday
    summarizeDue() -> { dueToday, overdue, due }

    DESIGN NOTE: "dismiss" and "snooze" live in SEPARATE FIELDS from dueAt.
    This is what guarantees the spec requirement "Do not reschedule a problem
    merely because the user dismissed a notification."

                tables: problems, attempts, revisions, events, catalog,
                        imports, meta
                schema v1 -> v2 (v2 adds catalog + imports and backfills

    *** CRITICAL ARCHITECTURAL RULE ***
    A content script's IndexedDB resolves to the PAGE'S ORIGIN (leetcode.com).
    Storing revision history there would expose it to the website.
    Therefore the service worker is the ONLY writer/reader of IndexedDB and
    all other contexts go through typed chrome.runtime.sendMessage.

4.6 TIMESTAMP NORMALISATION (src/utils/time.ts)
      < 1e11            -> Unix SECONDS
      >= 1e11           -> Unix MILLISECONDS
      numeric string    -> same rule as a number
      ISO 8601 / offset -> absolute
      "2026-10-21"      -> LOCAL midnight  (flagged as an ambiguity warning)
      "2026-10-21 09:30"-> LOCAL time      (flagged as an ambiguity warning)
      Date object       -> getTime()
      invalid/missing   -> rejected with a reason
    Threshold rationale: 1e11 ms = 1973, 1e11 s = year 5138, so the two
    interpretations never overlap for real data. Ambiguous FORMS are never
    silently shifted — they are read as local and reported in the preview.

4.8 SUBMISSION TRACKER (src/services/submissionTracker.ts)
    - Listens (capture phase) for a click on a <button>/[role=button] whose
      text matches /^submit\b/i and is NOT "Run Code".
    - Then watches for a verdict:
        * verdict-ish containers ([class*=verdict], [class*=toast],
          [role=alert], [role=status], [data-e2e-locator*=submission|result])
          matched with matchExactVerdict() — the WHOLE element text must be
          the verdict, which stops prose like "your solution is accepted"
          from being mistaken for a result
        * fallback: loose scan of the last 900 chars of document.body.innerText
    - Verdicts: Accepted, Wrong Answer, Runtime Error, Time Limit Exceeded,
      Memory Limit Exceeded, Output Limit Exceeded, Compilation Error,
      Answer Too Long
    - Same verdict is never recorded twice within 5 s.
    - detectLanguage(): best-effort, prefers a dropdown inside the editor,
      returns null rather than guessing.
    - Opening a problem NEVER records an attempt (markViewed only).

7. ARCHITECTURAL RULES — DO NOT UNDO THESE
--------------------------------------------------------------------------------

  1. SINGLE WRITER. All IndexedDB access lives in
     src/background/serviceWorker.ts -> src/services/repository.ts.
     Content script and UI pages use typed chrome.runtime.sendMessage
     (src/services/messaging.ts). Rationale in 4.4.

  2. THE REVISION ENGINE STAYS PURE. Every function in
     src/services/revisionEngine.ts takes `now` as an argument and never
     calls Date.now() internally. This is what makes it testable.

  3. CONTENT CSS ISOLATION. src/styles/content.css has NO preflight and
     scopes everything under `#recalllc-root { all: initial; ... }`.
     The .rlc-* classes set border/background/font/colour explicitly so the
     host page's resets cannot leak in and our styles cannot leak out.
     Tailwind's own `border` utility does not work in that bundle.

  4. ONE THEME SYSTEM. src/styles/palette.css holds the palette; the custom
     Tailwind `dark` variant is attribute based, so the extension pages set
     data-theme on <html> and the reminder sets it on #recalllc-root.

  5. DISMISS AND SNOOZE NEVER RESCHEDULE. They are separate fields
     (dismissedAt / snoozedUntil) from dueAt. Keep them separate.

  6. NO PASSWORDS, NO COOKIES, NO TELEMETRY, NO REMOTE CODE.

  7. DEMO DATA STAYS OUT OF PRODUCTION. Keep the import.meta.env.DEV guard.

11. DOCUMENTED IMPORT FORMAT (also in README.md)
--------------------------------------------------------------------------------

  JSON — each object is ONE attempt:
    {
      "slug": "two-sum",
      "title": "Two Sum",
      "url": "https://leetcode.com/problems/two-sum/",
      "attemptedAt": 1792454400000,
      "accepted": true,
      "language": "java",
      "submissionId": "optional-id"
    }
  Required: slug, attemptedAt. Everything else optional.
  The file may be a bare array, or an object with an
  attempts/problems/records/items/data/history array.

  CSV — first row must be a header. Loose, separator-insensitive matching:
    slug          : slug, titleSlug, title_slug, problemSlug, problem_slug,
                    questionSlug, name, problem, question
    timestamp     : attemptedAt, attempted_at, timestamp, time, date, datetime,
                    createdAt, created_at, submittedAt, submitted_at,
                    submissionTime, lastAttempted, last_attempted, solvedAt
    title         : title, problemTitle, questionTitle, name
    url           : url, problemUrl, link, href
    accepted      : accepted, isAccepted, success, solved, status, result,
                    verdict, outcome
    language      : language, lang, programmingLanguage, programming_language
    submission id : submissionId, submission_id, subId, id, submission

  Example CSV:
    slug,title,attemptedAt,accepted,language,submissionId
    two-sum,Two Sum,1792454400000,true,java,88012301
    coin-change,Coin Change,1792281600000,false,java,88014777

12. PRIVACY SUMMARY (as implemented)
--------------------------------------------------------------------------------

  permissions["storage"]           persist settings + revision schedule locally
  host_permissions leetcode.com    read the problem page you are already on,
                                   detect the current slug, detect the submit
                                   verdict, (opt-in) fetch the public catalogue

  RecallLC NEVER: asks for your LeetCode password; reads, stores or forwards
  session cookies (the browser attaches them to same-origin page requests, and
  RecallLC never sees them); sends your revision history anywhere; contains
  analytics, telemetry or remote code; modifies LeetCode's page; injects a
  solution or hint into the editor; requests tab URLs, cookies or history
  access.

  Imported files are untrusted input: every field is validated, and content is
  rendered as text, never as HTML.

13. DOCUMENTED LIMITATIONS (honest, not bugs waiting to be fixed)
--------------------------------------------------------------------------------

  - LeetCode's GraphQL is bot-protected, so catalogue/sync requests must be
    made from a page context while signed in. The public legacy endpoint works
    without a session but has no topic tags.
  - Automatic history retrieval is incomplete by design: `submissionList` is
    paginated and returns only a limited window of recent submissions.
    RecallLC cannot recover a complete archive and does not claim to. The
    import workflow is the complete path for bulk history.
  - Account sync is opt-in and off by default; it requires a signed-in
    leetcode.com visit and runs at most once every six hours. Review
    LeetCode's Terms of Service before enabling it.
  - LeetCode's DOM is not a stable API. The verdict detector uses several
    fallbacks but a redesign could break it. It fails silently rather than
    recording wrong data, and manual saving remains available as a fallback.
  - Difficulty and topics are best-effort and come from the public catalogue.
  - Premium problems are tracked by slug only; their editor and submissions
    are not read.
